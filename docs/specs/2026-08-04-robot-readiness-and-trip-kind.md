# 로봇 준비상태 표시 + 출장 성격(Domestic/Overseas) 구분
- 상태: draft
- 대상: cardconv (Review 🤖 / ✈ export), scripts/sap_trip_robot.py

## 문제

2026-08-04 실전 2회차에서 드러난 것 세 가지 중 두 가지가 남았다(창 자동닫힘·실행로그·종료코드는 `b797dbd`로 처리됨).

1. **화면이 로봇 상태를 모른다.** 🤖는 누르면 콘솔만 띄우고, 로봇은 최대 15분간 화면이 열리길 기다린다. 그래서 "누르면 되는 상태인지", "기다리는 중인지", "이미 끝났는지"를 화면에서 알 수 없다. 오늘 창이 아예 안 열렸을 때 원인을 못 찾은 것도 이 때문이다. 강프로 지적: *"준비가 완료되면 화면상에서 작업을 트리거할 무엇인가가 필요하다"*, *"언제 인식해서 처리하는가가 고민"*.
2. **출장의 Domestic/Overseas가 구분되지 않는다.** GTE 입력의 Vendor Name kind(`select#hbrdCdu`)는 Domestic/Overseas 둘 중 하나인데, 지금은 **로봇 실행 인자 `--domestic`** 로만 정해지고 기본값이 Overseas다. 한 번 정하면 그 실행의 모든 줄에 같은 값이 박힌다. 강프로 지적: *"출장이 어떤 건 Domestic이고 어떤 건 Overseas다. Export할 때부터 그 성격이 구분되면 좋겠다"*.

### 확인한 사실 (근거 표기)
- ✓ export가 `"currency": FIXED["currency"]` 로 **모든 줄에 USD를 하드코딩**한다 (`_cardconv_core.py:4365` 직접 읽음). 그래서 지금 JSON의 통화값으로는 국내/해외를 가를 수 없다.
- ✓ 로봇은 `--domestic` 유무로 전 줄 일괄 결정 (`sap_trip_robot.py` overseas 플래그).
- ? 거래별 실제 통화(`ocr_currency`)가 실데이터에 얼마나 채워져 있는지 **미확인**. prod 파일을 열어봤으나 구조가 달라 집계 실패 — 자동 추론을 설계 근거로 삼기 전에 이걸 먼저 재야 한다.

## 목표

- Review에서 🤖를 누르기 전에 **준비 상태 3가지**(로봇 Edge / 입력 화면 / export)를 화면에서 보고, 끝난 뒤 **결과**(N/M 저장, 실패 사유)를 화면에서 본다.
- 출장별 Domestic/Overseas를 **export 시점에 확정**해 JSON이 줄마다 싣고, 로봇은 그대로 따른다.

## 비목표 (이번엔 안 한다)

- 로봇을 웹에서 원격 실행하지 않는다. 트리거는 지금처럼 🤖(로컬 콘솔) — 브라우저에서 회사 시스템에 쓰는 경로는 만들지 않는다.
- 실시간 진행률(1/4, 2/4…) 스트리밍은 안 한다. 시작·종료 두 시점만 반영한다.
- 통화 자동 추론으로 성격을 **결정**하지 않는다(아래 Q2 참조). 기본값 제안까지만.
- 여러 출장 동시 처리는 지금대로 한 번에 하나.

## 사용자 흐름

1. Review에서 ✈ export → **출장별로 Domestic/Overseas를 고르는 작은 단계**를 거친다(기본값은 마지막 선택 기억)
2. 내려받은 JSON은 줄마다 `vendor_kind: "D"|"O"` 를 갖는다
3. Review의 🤖 옆에 **준비 상태 배지 3개**: `로봇 Edge` / `입력 화면` / `export` — 각각 ○/● 로 표시, 5초 폴링
4. 셋 다 준비되면 버튼이 `🤖 4건 기입` 처럼 건수를 말한다. 빠진 게 있으면 **무엇이 빠졌는지**와 할 일을 버튼 아래 한 줄로 안내
5. 로봇이 끝나면 같은 자리에 결과 표시: `✅ 4/4 저장` 또는 `⚠ 0/4 저장 — Save 거부됨`

## 데이터

**export JSON (줄 단위)**
- 신규 키: `vendor_kind` — `"D"`(Domestic) | `"O"`(Overseas). 기본 `"O"`(기존 동작과 동일)
- 마이그레이션: 없음. `vendor_kind` 없는 옛 JSON은 로봇이 `"O"`로 읽어 지금과 같게 동작
- 롤백: 옛 로봇은 이 키를 무시하고 `--domestic` 플래그를 쓴다 — 데이터 안 깨짐

**출장별 선택 저장**
- `user_settings_<user>.json` 에 `trip_kind: {"<출장명>": "D"|"O"}` 추가 (다음 export 때 기본값)
- 마이그레이션: 없음(없으면 빈 dict)

**상태 통로 (핵심 설계 결정 필요 — Q1)**
로봇은 WSL에서 돌고 웹앱도 같은 로컬 머신에서 돈다. 상태를 주고받을 가장 싼 통로는 **파일**이다.
- 로봇이 `/tmp/sap-robot-status.json` 을 시작·종료 시 쓴다: `{state, trip, total, saved, failures, at}`
- 웹앱은 `GET /cardconv/robot/status` 에서 그 파일 + **CDP로 Edge 상태 조회**(9223 중계기에 `/json/list` 한 번)를 합쳐 돌려준다
- **prod에는 이 경로가 없다** — 로봇은 로컬 전용이다. prod에서는 이 API가 항상 "로컬 전용" 을 답하고 배지를 숨긴다

## 영향 표면

- Review 화면(데스크탑/모바일), ✈ export 흐름
- prod/staging: 로봇은 로컬 전용 → **prod에서는 배지·상태 API가 조용히 비활성**. 이걸 안 지키면 prod Review에 영원히 회색 배지가 뜬다
- 권한: admin 전용(🤖가 이미 admin 전용)
- 모바일 425px: 배지 3개가 가로로 넘치지 않게
- 기존 딥링크·xlsx export: 영향 없음

## UX/UI

- 배지 = 기존 `tk-chip`/스탯칩 셰이프 재사용, 색은 토큰(`--green-500`/`--text-muted`)
- 출장 성격 선택 = 기존 **바텀시트/모달 공유 컴포넌트** 재사용(새 발명 금지)
- 결과 줄 = 기존 `wfProgress`/배너 패턴

## 리스크 / 미결 질문

- **Q1. 상태 통로를 파일+CDP 조회로 갈까요?** 웹앱이 5초마다 Edge에 한 번 물어보는 구조입니다. 대안은 로봇이 상태 파일만 쓰고 웹은 그 파일만 읽는 것(더 단순하지만, 로봇을 켜기 **전**에는 Edge가 열렸는지 알 수 없어 배지 3개 중 2개가 무의미해집니다). 쭌 추천은 **파일+CDP**.
- **Q2. Domestic/Overseas를 무엇으로 정할까요?**
  - (a) **출장별로 강프로가 한 번 선택** — 확실함, 출장당 클릭 1회. 쭌 추천.
  - (b) 통화로 자동(KRW=Domestic) — 클릭 0회지만, 지금 export가 통화를 USD로 하드코딩해서 **먼저 실제 통화를 싣는 작업이 선행**돼야 하고 그게 얼마나 채워져 있는지도 미확인입니다.
  - (c) 줄 단위로 각각 지정 — 가장 정확하나 건수만큼 손이 갑니다.
- **Q3.** 이번 회차에 둘 다 할까요, 아니면 **출장 성격(Q2)을 먼저** 하고 상태 배지는 다음으로 미룰까요? 성격 구분은 지금 기입 정확도에 바로 영향을 주고, 배지는 편의입니다.
