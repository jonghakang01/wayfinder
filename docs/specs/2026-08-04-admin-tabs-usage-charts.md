# 관리자 페이지 탭 구조 + Usage 그래프
- 상태: shipped (2026-08-04)
- 대상: admin (`/admin`, `/admin/usage`)

## 강프로 결정 (미결 질문 해소)
- **Q1 → 탭 2개** (`Users` / `Usage`). System 3번째 탭은 안 만든다.
- **Q2 → A + B 채택, C는 안 함.** 앱별 핵심 액션 계측은 별건으로 미룬다.
- **Q3 → 관리자 화면 영문화 진행.** 한글 UI 19건을 영문으로 옮겨 린트 부채를 갚는다.

## 문제

1. **관리자 화면이 두 페이지로 갈라져 있다.** 사용자 관리는 `/admin`, 사용량은 `/admin/usage`. 두 화면을 오가려면 "← Admin" 링크로 되돌아가야 하고, 두 화면이 서로 다른 셸(nav·제목·카드 스타일)을 쓴다.
2. **Usage가 표뿐이다.** 숫자는 있는데 "늘고 있나 줄고 있나"를 눈으로 볼 수 없다. 추세는 표의 행을 머릿속으로 비교해야만 나온다.
3. **`/admin`은 디자인 시스템 밖에 있는 마지막 화면이다.** 린트 baseline 기준 위반 64건(하드코딩 색 44, 한글 UI 19, 모바일 브레이크포인트 없음 1) — webapp에서 가장 큰 부채 덩어리다. `_usage.py`는 0건으로 이미 토큰 기반이다.

## 목표

- `/admin` 한 페이지 안에서 **Users / Usage** 두 탭으로 전환한다 (cardconv·Momentum과 같은 pill 탭).
- Usage 탭에서 **추세를 그림으로** 본다: 일별 방문 추이, 앱별 점유, 사용자 활동 히트맵.
- `/admin`을 디자인 시스템으로 옮겨 린트 부채를 줄인다(단조 감소 원칙).

## 비목표 (이번엔 안 한다)

- **새 추적 항목 구현 안 한다.** 아래 "추가 추적 후보"는 제안까지만 — 채택된 것만 별건 스펙으로.
- 30일 고정 기간 유지. 기간 선택기(7/30/90일)는 별건.
- 사용자 관리 기능 자체의 변경 없음(역할·서비스·차단·비번 초기화 로직은 그대로, 껍데기만 탭 안으로).
- CSV/엑셀 내보내기 없음.
- 차트 라이브러리 도입 없음 — 기존 방식(CSS 막대 + 인라인 SVG)을 따른다.

## 사용자 흐름

1. admin 계정으로 `/admin` 진입 → 상단에 `👤 Users` / `📊 Usage` pill 탭
2. 기본은 Users 탭 — 지금의 사용자 표·전역 서비스 제어·테스터 대기열·공지 발송이 그대로
3. `📊 Usage` 클릭 → `/admin?tab=usage` (딥링크 가능) → 스탯카드 4개 + 그래프 3종 + 기존 표 2종
4. 앱 이름 클릭 → 그 앱의 사용자별 드릴다운 (`/admin?tab=usage&app=/cardconv`) — 기존 동작 유지

## 데이터

Q2 결정(B 채택)으로 **기록 스키마가 바뀐다** — 초안의 "변경 없음"을 여기서 정정한다.

- 파일: `~/.appdata/usage/<YYYY-MM>.jsonl` (경로·형식 그대로)
- 기존 키: `d`(날짜) `u`(사용자) `a`(앱)
- **신규 키**
  - `h` (int 0–23, 기본 없음) — 그 시각에 열었다
  - `m` (int 1 = 모바일, 없으면 데스크탑) — User-Agent 판정
- **중복 제거 단위 변경**: `(날짜, 사용자, 앱)` → `(날짜, 사용자, 앱, 시각)`
  - 하루 최대 24행/사용자/앱으로 상한이 걸린다
  - **왜 진짜 클릭 수를 안 세나**: `record()`가 서비스 디스패치 지점에 있어 cardconv 폴링·서브경로 요청까지 전부 탄다. 매 요청 1행이면 폴링 하나로 파일이 폭증한다. 그래서 강도 지표는 **"활동한 시간대 수(active hours)"**로 부르고, "방문 N회"라고 쓰지 않는다.
- **마이그레이션**: 없음. 기존 행에는 `h`·`m`이 없고, 읽는 쪽이 `None`으로 취급해 "시각 미상"으로 집계에서 빠진다. 옛 행이 새 코드에서 사라지거나 중복되지 않는다.
- **롤백**: 옛 코드는 `d/u/a`만 읽으므로 새 행도 정상 인식된다(`h`·`m` 무시). 단 옛 코드의 중복 제거는 `(d,u,a)`라 같은 날 여러 시각 행이 각각 1방문으로 세어져 **방문일수가 부풀어 보인다**. 데이터 손상은 아니다.
- 로컬/프로덕션 기존 데이터: prod 12행 · 로컬 6행. 전부 `h`·`m` 없는 옛 행이다.
- `/admin/usage` 옛 경로는 `/admin?tab=usage`로 **리다이렉트 유지** (북마크·기존 링크 보호)

### 데이터 현실 (2026-08-04 실측)
- prod 사용량 기록 **12행**, 사용자 10명. Usage 기능이 2026-08-03에 켜져서 **데이터가 이틀치뿐**이다.
- → 30일 그래프는 당분간 막대 2~3개만 선다. **이건 버그가 아니라 정상**이며, 빈 구간을 0으로 그려서 "아직 쌓이는 중"이 보이게 한다.
- `users.json`에 **가입일자(created_at)가 없다** → "신규 가입 추이"·"코호트 잔존율"은 지금 데이터로 못 만든다.

## 추가 추적 후보 (제안 — 이번 스펙의 비목표, 채택된 것만 별건 진행)

지금 저장하는 것은 `(날짜, 사용자, 앱)` 한 줄뿐이고 **하루에 한 번만 기록**된다(같은 앱을 열 번 열어도 1행). 그래서 "얼마나 자주"·"몇 시에"는 원리적으로 답할 수 없다.

### A. 지금 데이터로 바로 되는 것 (추가 추적 0, 계산만)
| 항목 | 무엇을 알려주나 | 비고 |
|---|---|---|
| **DAU/MAU 고착도** | 월 사용자 중 몇 %가 오늘도 왔나 = 습관이 됐는지 | 비율 하나로 제품 건강도 요약 |
| **휴면 사용자** | 가입은 했는데 N일째 안 들어온 사람 | users.json ∖ 최근 usage. 이탈 조기경보 |
| **앱별 재방문율** | 한 번 써본 사람 중 다시 온 비율 | 앱이 일회성인지 도구인지 구분 |
| **사용자당 앱 수** | 한 사람이 며칠에 몇 개 앱을 쓰나 | 교차 사용(cross-use) 지표 |

### B. 기록 한 줄 추가로 되는 것 (`record()`에 필드 1~2개)
| 항목 | 무엇을 알려주나 | 비용 |
|---|---|---|
| **시각(hour)** | 언제 쓰나 — 업무시간 도구인지 퇴근 후 도구인지 | `d`에 시각 추가. 파일 크기 그대로 |
| **방문 횟수** | 하루 1회 vs 20회 — 진짜 사용 강도 | 하루 1행 유지하되 `n` 카운터 증가 |
| **모바일/데스크탑** | 폰 대응 우선순위의 근거 | User-Agent 한 글자(`m`/`d`) |
| **유입 경로** | 홈에서 왔나, 딥링크·폰 바로가기인가 | Referer 기반, 정확도 한계 있음 |

### C. 계측이 필요한 것 (앱별 코드 삽입 — 진짜 일)
| 항목 | 무엇을 알려주나 | 비용 |
|---|---|---|
| **핵심 액션 수** | 방문이 아니라 **성과** — 영수증 N건 변환, 계약 N건 추출, 할 일 N건 완료, 건배사 N건 조회 | 앱마다 지점 지정 필요. 가장 값진 지표이자 가장 비쌈 |
| **실패·에러율** | 앱별 5xx, OCR 실패, 외부 API 실패 | 사고를 사용자가 말하기 전에 발견 |
| **응답 지연(p95)** | 53차 영수증 504 같은 사고의 조기 신호 | 디스패치에서 시간 측정 |
| **로그인 실패** | 계정 문제·침입 시도 | 보안 신호 |

### 쭌 추천 (돈 대비 값)
1. **A 전부** — 추가 추적 없이 계산만으로 나오므로 이번 개편에 같이 넣어도 비용이 거의 0
2. **B의 시각 + 방문 횟수** — 한 줄 수정으로 "얼마나 자주·언제"가 열린다
3. **C는 '핵심 액션 수'만**, 그것도 cardconv 한 곳부터 — 전 앱 계측은 과하다
