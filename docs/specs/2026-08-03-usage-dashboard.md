# 활용도 대시보드 (Usage)
- 상태: approved (2026-08-03 강프로 — Q1 포함, Q2 제외)
- 대상: server.py (기록 지점) + admin (열람 화면)

## 문제
어떤 앱을 누가 얼마나 쓰는지 볼 방법이 없다. 서버는 접근 로그를 꺼둔 상태라
(`server.py::log_message` no-op) 방문 기록이 어디에도 남지 않는다. 앱별 투자
우선순위·사용자별 온보딩 상태를 감이 아니라 데이터로 판단하고 싶다는 요청
(강프로, 2026-08-03).

## 목표
- 요청이 서비스로 디스패치될 때마다 `날짜·사용자·앱` 방문 기록이 자동으로 쌓인다
  (앱 코드 수정 없이 server.py 한 지점).
- 관리자가 `/admin/usage`에서 앱별·사용자별 활용도를 본다:
  앱별 30일 활성 사용자·방문일수, 사용자별 마지막 활동·주사용 앱, 앱×날짜 표.

## 비목표 (이번엔 안 한다)
- 클릭 수·페이지뷰·체류시간 측정 — 단위는 "그 날 그 앱을 열었나"(일 단위 방문)뿐.
- 앱 내부 탭/기능 단위 세분화 (앱 경로 단위까지만).
- 과거 소급 — 배포 시점부터 쌓인다. 파일 수정시각 기반 추정도 안 넣는다.
- 일반 사용자용 노출 — admin 전용.
- export(xlsx/CSV)·알림·리텐션 곡선 등 분석 고도화.

## 사용자 흐름
1. (기록) 로그인 사용자가 아무 앱이나 열거나 조작 → 서버가 (오늘, 사용자, 앱)
   한 줄 기록. 같은 날 같은 앱 재방문은 중복 기록 안 함.
2. (열람) 관리자가 /admin 상단 링크로 /admin/usage 진입
3. 스탯카드(30일 활성 사용자 / 오늘 활성 / 가장 많이 쓰인 앱) + 앱별 표 +
   사용자별 표를 본다. 앱 행을 클릭하면 그 앱의 사용자별 방문일수로 드릴다운.

## 데이터
- 신규: `DATA_ROOT/usage/<YYYY-MM>.jsonl` — 한 줄 = `{"d":"2026-08-03","u":"<이메일>","a":"/toast"}`
  - 월별 파일 분리(무한 성장 방지, 파일당 수 KB 수준)
  - append 전용 + 서버 메모리의 (날짜,사용자,앱) seen-set으로 일 단위 중복 제거.
    서버 재시작 시 당월 파일을 읽어 seen-set 복원 → 재시작해도 하루 1건 유지.
  - ThreadingHTTPServer 동시 요청 대비 쓰기 lock 1개.
- 기록 지점: server.py do_GET/do_POST의 SERVICES 디스패치 직전(권한 통과 후).
  ctx["user"] 있는 요청만 — /health·정적파일·/login·비세션 웹훅(arrive, batch)은
  구조상 제외됨.
- 마이그레이션: 없음 (신규 파일만 추가, 기존 데이터 무접촉)
- 롤백: usage/ 파일이 남아도 다른 코드가 읽지 않으므로 무해.
- staging/prod 격리: DATA_ROOT 하위라 자동 분리.

## 영향 표면
- 홈 메뉴: 영향 없음 (새 앱 아님, admin 내 화면 추가)
- 다른 탭/export/딥링크/알림: 영향 없음
- 모바일 390px / 라이트 테마: usage 화면이 양쪽 지원해야 함 (수용 조건에 포함)
- 권한: admin_only. cardconv @pid 프로필은 로그인 계정 단위로만 집계(프로필 세분화 안 함).
- 성능: 요청당 추가 비용 = set 조회 1회 + (신규일 때만) 파일 append 1줄 — 무시 가능.

## UX/UI
재사용: 클릭형 스탯카드 + 카드테이블(공유 컴포넌트) + pill 링크. 신규 패턴 발명 없음.
앱×날짜 표는 기존 테이블 토큰으로 (히트맵 색상 발명 금지, 방문일수 숫자 표기).

## 수용 조건 (테스트 가능하게)

- [ ] 서버 재시작 후 같은 날 재방문해도 중복 기록 없음

- [ ] 비관리자가 /admin/usage 접근 시 차단
